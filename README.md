# 🎰 Discord Interactive Casino Bot v2

discord.js v14 + MongoDB(Mongoose) 기반 **가상 칩** 카지노 봇입니다.
게임 결과는 `crypto` CSPRNG로 **선(先) 연산**되고, 칩은 베팅 순간 **에스크로**로 묶였다가 판이 끝날 때 **한 번만** 정산됩니다.
서버가 죽어도 결과가 정해진 판은 그 결과대로, 정해지지 않은 판은 환불로 복구됩니다.

> ⚠️ 이 봇의 칩은 현금·상품으로 환전할 수 없는 순수 게임 재화로만 운영하세요. 환전이 붙는 순간 사행행위 관련 법령의 적용을 받을 수 있습니다.

## 🧠 아키텍처

### 칩의 생애: 에스크로 정산

```
베팅      reserve()       money ≥ 베팅액일 때만  money −= 베팅액, escrow += {roundId}
추가 베팅 addStake()      (더블·스플릿·보험·레이즈)  money ≥ 추가액일 때만
결과 확정 commitResult()  escrow.pendingPayout = 지급액      ← 연출 전에 기록 (write-ahead)
판 종료   settle()        escrow에 roundId가 있을 때만  money += 지급액, escrow −= {roundId}
취소      refund()        escrow에 roundId가 있을 때만  money += 원금, escrow −= {roundId}
```
- **원자성:** 모든 잔고 변경은 지갑 문서 1개에 대한 단일 업데이트라서 트랜잭션 없이도 원자적입니다.
- **멱등:** 같은 roundId로 정산이 두 번 오거나 정산과 환불이 경합해도, 정확히 한 번만 반영됩니다.
- **이중 사용 불가:** 잔고 검사가 DB 조건(`$gte`)에서 이뤄지므로 동시에 여러 판을 걸어도 잔고를 넘을 수 없고, 음수 잔고도 생기지 않습니다.
- **게임 외 칩 이동**(출석·지원금·관리자 지급/회수·상점·시즌 보상)은 모두 `Ledger`에 발행(+)/회수(−)로 기록됩니다.

### 장애 복구 정책

| 상황 | 처리 |
|---|---|
| 정상 종료 (SIGTERM, 재배포) | 이 프로세스의 판: 결과 확정 → 정산, 미확정 → 환불 |
| 재시작 (`RECOVER_ON_BOOT=true`) | 이전 프로세스의 판을 부팅 즉시 같은 규칙으로 처리. 열려 있던 게임은 `CANCELLED`/`COMPLETED`로 닫고, 디스코드 메시지에 안내를 남김 |
| 크래시 후 다른 인스턴스 | 1분마다 스윕: 기본 20분(포커 1시간, 토너먼트 3시간) 지난 미정산 판을 같은 규칙으로 처리 |
| 정산 중 DB 오류 | 게임을 `RECOVERY_REQUIRED`로 표시하고 알림 → `/관리자 복구 [게임id]`로 재시도 |
| 비정상 종료 | 하트비트로 감지해 다음 부팅 때 알림 |

**결과가 "확정"되는 시점 (게임별):**
- 슬롯·주사위·바카라: 결과 계산 직후, 연출 전
- 블랙잭: 딜러 플레이 후 판정 시점
- 그래프: 자동 캐시아웃 판은 시작 시점(폭발 배수와 목표를 알기 때문), 수동 판은 캐시아웃·폭발 시점
- 포커·토너먼트: 핸드·토너먼트 종료 시점

진행 중이던 판의 "중간 상태"(예: 블랙잭 손패 도중)를 이어서 재개하지는 않습니다. 이유는 두 가지입니다. 디스코드 인터랙션이 끊긴 상태에서 재개하는 경험이 좋지 않고, "미확정 판은 환불"이 더 단순하고 안전하기 때문입니다.

### 게임 상태 머신
`CREATED → BETTING → PLAYING → SETTLING → COMPLETED`, 예외 상태는 `CANCELLED`와 `RECOVERY_REQUIRED`입니다. 테이블·세션마다 기록되며, 부팅 복구와 `/관리자 복구`가 이를 사용합니다.

### 이벤트 버스
정산이 끝나면 `round:settled` 이벤트가 발생하고, 프로필 서비스가 이를 받아 누적 전적·연승·미션·업적을 갱신합니다. 정산 코드는 업적·미션을 모르고, 리스너의 오류는 정산에 전파되지 않습니다.

### 실시간 편집·동시성
- `LiveMessage`는 latest-wins 방식이라 레이트 리밋에 걸려도 화면이 밀리지 않습니다.
- 테이블 락(`runExclusive`)과, 바쁘면 재시도하는 타이머(`runSoon`)로 버튼 연타와 타이머 유실을 막습니다.
- 인터랙션 토큰(15분)이 만료되면 봇 토큰으로 메시지를 직접 편집하도록 자동 전환됩니다.

### 📊 이론 RTP (지급액 ÷ 베팅액)

| 게임 | 기본 설정 | RTP |
|---|---|---|
| 슬롯 | 🍒×3 🍋×8 🔔×15 💎×100 7️⃣×777 · 🍒🍒×1.25 | 94.5% (+ 잭팟 풀 약 1%) |
| 그래프 | 하우스 엣지 3% · 0.80x 출발 | 97% (1.00x 이상 탈출 기준, 본전 전 탈출은 더 낮음) |
| 주사위 | Hi/Lo ×2, 7 ×5 | 83.3% (×2.3 / ×5.7로 올리면 약 95%) |
| 바카라 | P ×2 / B ×1.95 / T ×9 | 98.8% / 98.9% / 85.6% |

### 웹 대시보드 (읽기 전용)
`DASHBOARD_TOKEN`을 설정하면 헬스 체크 서버에 `/dashboard?token=…`(HTML)과 `/api/overview?token=…&guild=…`(JSON)이 열립니다. 쓰기 작업은 일부러 넣지 않았습니다. 관리 작업은 감사 로그가 남는 `/관리자`로만 합니다.

### 장애 알림
`ALERT_WEBHOOK_URL`(디스코드 채널 웹훅)로 다음 상황을 알립니다: DB 연결 끊김, 정산 실패, 부팅 복구 결과, 비정상 종료 감지, 디스코드 연결 끊김, 처리되지 않은 오류, 백업 실패. 같은 제목은 1분에 한 번만 보냅니다.

### 백업과 복원
```bash
npm run backup                                   # backups/backup-<시각>/ 에 저장 + 무결성 검사
npm run restore -- backups/backup-… --verify     # 체크섬·파싱·문서 수 확인
npm run restore -- backups/backup-… --apply --uri <대상URI> --yes [--drop]
```
`.github/workflows/backup.yml`이 매일 03:00(KST)에 다음을 실행합니다.
1. 운영 DB를 백업합니다.
2. **임시 MongoDB 컨테이너에 실제로 복원**해 컬렉션별 문서 수를 대조합니다(복원 리허설).
3. 백업을 14일간 아티팩트로 보관합니다.

저장소 Secrets에 `MONGODB_URI`(필요하면 `ALERT_WEBHOOK_URL`도)를 등록해야 합니다. **아티팩트에 유저 데이터가 들어가므로 private 저장소에서만 쓰세요.**

### 경제 범위
- `ECONOMY_SCOPE=guild`(기본): 서버마다 지갑·랭킹·시즌·잭팟이 독립입니다. 프로필(업적·칭호·포인트·꾸미기)은 모든 서버에서 공통입니다.
- `ECONOMY_SCOPE=global`: 모든 서버가 지갑 하나를 공유합니다.

## 🚀 설치와 배포

### 1단계 — 디스코드 봇 만들기

1. [Discord Developer Portal](https://discord.com/developers/applications) → **New Application**
2. **General Information** → `Application ID` 복사 → `CLIENT_ID`
3. **Bot** 탭 → **Reset Token** → 토큰 복사 → `DISCORD_TOKEN` (한 번만 보이니 바로 보관)
   - Privileged Gateway Intents는 **모두 꺼둔 상태로 OK** (슬래시 명령어만 사용)
4. **OAuth2 → URL Generator**
   - Scopes: `bot`, `applications.commands`
   - Bot Permissions: `View Channels`, `Send Messages`, `Embed Links`, `Attach Files`(프로필 이미지), `Read Message History`, `Create Public Threads`·`Send Messages in Threads`(토너먼트 스레드 — 없으면 같은 채널에서 진행)
   - 생성된 URL로 서버에 초대

### 2단계 — MongoDB Atlas

1. [MongoDB Atlas](https://www.mongodb.com/atlas)에서 무료 클러스터 생성
2. **Database Access** → DB 유저 생성 (비밀번호에 `@ : /` 등이 있으면 URL 인코딩 필요)
3. **Network Access** → `0.0.0.0/0` 허용 (Koyeb의 아웃바운드 IP는 고정이 아님)
4. **Connect → Drivers** → 연결 문자열 복사, 호스트 뒤에 DB 이름(`/casino`)을 붙여 `MONGODB_URI`로 사용

### 3단계 — 로컬 실행

```bash
npm install
cp .env.example .env      # 값 채우기 (DEV_GUILD_ID를 넣으면 명령어가 즉시 반영됨)
npm run check             # 단위 테스트 + E2E (DB 없이 실행)
npm start
```

### 4단계 — GitHub 업로드

```bash
git init
git add .
git commit -m "init: discord casino bot"
git branch -M main
git remote add origin https://github.com/<계정>/discord-casino-bot.git
git push -u origin main
```
`.env`는 `.gitignore`에 들어 있어 올라가지 않습니다.

#### package-lock.json (명령어 없이 만들기)
저장소에 push하면 `.github/workflows/lockfile.yml`이 GitHub 서버에서 `npm install`을 실행해 `package-lock.json`을 만들고 자동 커밋합니다.
- 웹에서 업로드했다면 **Actions** 탭 → *Generate package-lock.json* → **Run workflow**로 수동 실행해도 됩니다.
- 커밋 단계에서 403 오류가 나면 **Settings → Actions → General → Workflow permissions**를 *Read and write*로 바꾼 뒤 다시 실행하세요.
- lock 파일이 생기기 전이라도 Koyeb 빌드팩은 `npm install`로 정상 빌드합니다. lock 파일은 이후 배포마다 같은 버전을 쓰게 고정하는 역할입니다. 토큰이 실수로 커밋되면 즉시 Developer Portal에서 **Reset Token** 하세요.

### 5단계 — Koyeb 배포 (GitHub 연동 + Buildpack)

1. Koyeb 대시보드 → **Create Service** → **GitHub** → 저장소 선택, 브랜치 `main`
2. **Builder: Buildpack** — `package.json`의 `engines`로 Node 버전을, `scripts.start`로 실행 명령(`npm start` → `node index.js`)을 자동 인식합니다.
3. **Environment variables** — 토큰류는 Secret으로 등록

   | 키 | 값 |
   |---|---|
   | `DISCORD_TOKEN` | (Secret) 봇 토큰 |
   | `MONGODB_URI` | (Secret) Atlas 연결 문자열 |
   | `CLIENT_ID` | Application ID |
   | `REGISTER_COMMANDS` | `true` (부팅 시 명령어 자동 등록 — Koyeb엔 셸이 없으므로 권장) |
   | `DEV_GUILD_ID` | (선택) 테스트 서버 ID. 운영 시엔 비워서 전역 등록 |
   | `ECONOMY_SCOPE` | `guild`(기본, 서버별 지갑) 또는 `global` |
   | `BOT_OWNER_IDS` | (선택) 봇 소유자 ID, 쉼표 구분 |
   | `ALERT_WEBHOOK_URL` | (Secret, 선택) 장애 알림 디스코드 웹훅 |
   | `DASHBOARD_TOKEN` | (Secret, 선택) 웹 대시보드 토큰 |

4. **서비스 타입**
   - **Web Service**로 만들 경우: 포트 `8000`을 노출하고 헬스 체크를 이 포트로 지정하세요. `index.js`에 헬스 체크용 HTTP 서버가 내장되어 있습니다.
   - **Worker**로 만들 경우: 포트 설정 없이 그대로 동작합니다.
5. **인스턴스는 1개로 고정**하세요. 칩은 에스크로 덕분에 인스턴스가 여러 개여도 안전하지만, 테이블·게임 진행 상태는 프로세스 메모리에 있고 같은 봇 토큰으로 두 프로세스가 로그인하면 이벤트가 양쪽에 들어가 버튼 처리가 꼬입니다. 재배포 시 새 인스턴스가 먼저 뜨면 부팅 복구가 아직 살아 있는 이전 인스턴스의 판을 정리할 수 있습니다. 이때도 정산과 환불 중 정확히 하나만 반영되어 칩은 안전하지만, 그 판은 결과 대신 환불될 수 있습니다. 트래픽이 없을 때 인스턴스를 재우는 기능(scale-to-zero/sleep)이 켜져 있다면 꺼야 봇이 오프라인이 되지 않습니다.
6. **Deploy** → 로그에 `✅ 로그인`, `📝 슬래시 명령어 N개 등록`이 보이면 완료. 이후 `main`에 push할 때마다 자동 재배포됩니다.

> 전역 명령어는 디스코드 쪽 반영에 시간이 걸릴 수 있습니다. 개발 중엔 `DEV_GUILD_ID`를 쓰면 즉시 반영됩니다.

## ⬆️ v1에서 업그레이드

v2는 지갑의 고유 키가 `userId`에서 `(userId, guildId)`로 바뀝니다. **마이그레이션 없이 배포하면 서버별 지갑 생성이 실패합니다.**

1. 봇을 정지합니다 (Koyeb에서 서비스 Pause).

3. `npm run migrate`로 드라이런을 실행해 바뀔 내용을 확인합니다.
4. `npm run migrate -- --apply`로 적용합니다. 경제 키 정리, 에스크로·게임 기록 보강, 인덱스 교체가 일어납니다.
5. v2 코드를 push하고 서비스를 재개합니다.

`ECONOMY_SCOPE=guild`에서는 v1 지갑이 v1에서 **마지막으로 명령어를 쓴 서버**의 지갑이 됩니다. 다른 서버에서는 새 지갑(기본 잔고)으로 시작합니다. v1에서도 모든 서버가 지갑 하나를 공유했다면 `global`로 두는 것이 가장 자연스럽습니다.

## ⚠️ 알려진 한계

- **통계 집계 미검증:** MongoDB aggregation(대시보드·밸런스·랭킹 일부·시즌 결과)은 인메모리 테스트로 검증할 수 없어서 실제 DB에서 확인이 필요합니다.
- **단일 인스턴스 전제:** 테이블 진행 상태는 프로세스 메모리에 있으므로 인스턴스는 1개로 운영하세요. 칩 안전성은 다중 인스턴스에서도 유지됩니다.
- **판 중간 재개 없음:** 진행 중이던 판을 중간부터 재개하지 않고, 위 복구 정책을 따릅니다.
- **미적용 항목:** Redis와 다국어(i18n)는 넣지 않았습니다. Redis는 현재 구조(단일 인스턴스 + DB 에스크로)에서는 이득이 작습니다. 다중 인스턴스가 필요해지면 디스코드 샤딩부터 적용하는 것이 순서입니다.
- **웹 대시보드:** 읽기 전용입니다.
