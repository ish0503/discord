명세서 「DISCORD CASINO BOT 통합 수정 및 추가 기능 개발 명세서」를 기준으로 `claude/tournament-thread-profile-3nzz1x` 브랜치에서 단계별로 작업했다. 단계마다 커밋을 나눠 문제가 생기면 그 단계만 되돌릴 수 있다.

| 단계 | 커밋 제목 |
|---|---|
| 1 | 1단계 안정화: Outbox·복구 전적·송금 원자성·정산 검증·대시보드 인증·단일 인스턴스 |

| 3 | 3단계: 클랜(이용자 길드) · 월드 보스 · 클랜 순위·업적 · 배지/프로필 연동 · 수집품 기반 |

## 0. 이름 규칙: "길드" → 클랜

이 코드베이스에서 `guildId`는 처음부터 **디스코드 서버**를 뜻한다. 명세의 이용자 모임 "길드"를 같은 이름으로 만들면 `guildId`(서버)와 길드 ID가 섞여 데이터 격리 버그가 생기기 쉽다. 그래서 이용자 길드는 **클랜(Clan)** 으로 구현했다. 모델·서비스·명령어도 모두 이 이름을 쓴다(`Clan`, `ClanMember`, `/클랜`).

## 1. 기존 코드 안정성 수정 (1단계)

### [1-1] 정산 이벤트 Outbox

- **정산과 같은 원자적 업데이트로 기록:** `wallet.settle()`과 `refund()`가 칩 변경(`$inc money`, `$pull escrow`)과 같은 단일 문서 업데이트로 `User.outbox`에 이벤트를 `$push`한다. 트랜잭션 없이도 "칩은 바뀌었는데 이벤트가 없음" 상태가 생기지 않는다.
- **이관:** `services/outbox.js`가 지갑 문서의 이벤트를 `OutboxEvent` 컬렉션으로 옮긴다. `eventId`가 고유 인덱스라 여러 번 옮겨도 한 개만 남는다.
- **처리:** 이벤트를 원자적으로 점유(lease 60초)한 뒤 등록된 핸들러를 순서대로 실행한다. 끝난 핸들러는 `done`에 기록되고, 재시도 때는 남은 핸들러만 실행한다.
- **실패:** `attempts`와 `lastError`를 기록하고 지수 백오프로 재시도한다. 8회를 넘기면 `dead` 상태로 두고 알림을 보낸다. `/관리자 정산상태 재시도:True`로 다시 처리할 수 있다.
- **재시작:** 부팅 직후와 30초마다 `sweep()`이 지갑에 남은 이벤트를 이관하고, 미처리·실패·점유 만료 이벤트를 처리한다.
- **핸들러 멱등성:** 각 핸들러는 대상 문서에 처리 표식(`processedEvents`, `processed`)을 남긴다. 효과와 표식을 같은 조건부 업데이트로 반영해서, 같은 이벤트를 몇 번 처리해도 결과는 한 번만 들어간다.
- **등록된 핸들러:** gamelog, profile, rule, story, hof, clan, boss, collection, rank, rival.
- **정산 보호:** 이벤트 처리 실패는 이미 끝난 칩 정산에 영향을 주지 않는다. 칩은 1단계 업데이트에서 이미 끝난다.

### [1-2] 복구 게임의 전적·미션 보존

- **같은 경로 사용:** 예전에는 `onRoundSettled`가 `recovered`인 판을 건너뛰었다. 이제 복구 정산도 일반 정산과 같은 `settle → Outbox` 경로라서 전적·연승·미션·업적·클랜·랭크에 모두 반영된다.
- **중복 방지:** `settle:<roundId>` eventId와 에스크로 `roundId` 덕분에 같은 복구를 두 번 적용해도 한 번만 반영된다.
- **감사 기록:** 복구 정산·환불마다 `actorId: 'system'` 감사 로그를 남긴다(`recovery.settle`, `recovery.refund`).
- **복구 불가능한 판:** 검증 실패로 `blocked`된 판은 자동 복구가 정산하지 않는다. `/관리자 복구 게임id:`로 재시도하면 **원금 환불**만 하고 감사 기록(`recovery.blocked-refund`)을 남긴다.

### [1-3] 송금 일일 한도 원자성

- **흐름:**
  1. `Transfer`를 `transferId` 고유로 생성한다. transferId는 확인 버튼의 interaction ID라서 연타하거나 같은 요청이 다시 와도 기존 결과를 돌려준다.
  2. **한도 예약:** `TransferQuota.used ≤ 한도 − (금액+수수료)`일 때만 `$inc`한다. 동시 요청이 와도 합계가 한도를 넘지 않는다.
  3. **보낸 사람 차감:** 잔고 조건과 함께, 지갑 `txLog`에 `out:<id>`가 없을 때만 차감한다. 차감과 표식은 한 번의 업데이트다.
  4. **받는 사람 지급:** `in:<id>`가 없을 때만 지급한다.
  5. 원장에 기록한다. `refId` 부분 고유 인덱스로 중복을 막는다.
- **실패:** 실패하면 예약한 한도를 반환하고(pending→failed로 바꾼 쪽만, 한 번) 양쪽 잔고는 변하지 않는다.
- **중단 복구:** `recoverTransfers()`가 처리한다. 이미 차감된 거래는 받는 쪽 지급까지 마저 끝내고, 차감 전에 멈춘 거래는 실행하지 않고 취소한다.
- **입력 검증:** 자기 자신, 봇, snowflake가 아닌 ID, 0·음수·소수, 한도 초과 금액을 거부한다. 한도는 경제 단위(서버)마다 따로 센다.

### [1-4] 에스크로 정산 선기록·검증

- **지급액 검증:** `content/settlementRules.js`가 게임 규칙상 나올 수 있는 최대 지급 배수(+잭팟 풀)로 지급액을 검증한다. `commitResult()`(선기록)와 `settle()` 모두 검증한다.
- **검증 실패:** 지갑을 바꾸지 않는다. 그 판을 `blocked`로 표시하고, 감사 로그(`settlement.rejected`), `RECOVERY_REQUIRED`, 알림을 남긴다.
- **다인 정산:** 포커 핸드·토너먼트·예측은 `settlement.batch()`를 쓴다.
  1. 참가자·금액 불변식을 검사한다. 포커는 핸드 전후 테이블 칩 보존, 토너먼트는 상금 합계 = 상금 풀 ≤ 참가비 합, 예측은 지급 합계 = 걸린 칩 합이다.
  2. `SettlementRecord`를 선기록한다.
  3. 전원 결과를 선기록한다.
  4. 정산한다.
  5. 상태를 `applied`, `partial`, `rejected` 중 하나로 기록한다.
- **재호출:** 같은 `settlementId`로 다시 부르면 이미 적용된 참가자는 건너뛴다. 지갑도 `roundId`로 멱등이다.
- **부분 정산:** 일부만 정산되면(`partial`) 자동으로 다시 지급하지 않는다. 남은 판은 에스크로 복구 대상으로 남기고 관리자 확인 표시를 한다.
- **점검:** `/관리자 정산상태`로 Outbox, 다인 정산, 보류된 판, 처리 중 송금, 주기 작업 상태를 본다.

### [1-5] 대시보드 인증 개선 — **동작이 바뀜**

- **URL 토큰 폐지:** `?token=` 방식을 없앴다. 이제 거부되고 기록된다. 로그인 폼에서 토큰을 확인하면 HttpOnly·SameSite=Strict 세션 쿠키를 발급한다(HTTPS면 Secure). API는 `Authorization: Bearer`도 받는다.
- **토큰 비교:** 토큰은 32자 이상이어야 하고 짧으면 대시보드가 꺼진다. 비교는 SHA-256 다이제스트끼리 `timingSafeEqual`로 해서 길이가 드러나지 않는다.
- **만료·재발급·폐기:**
  - 세션 만료: 기본 1시간
  - 토큰 만료: `DASHBOARD_TOKEN_EXPIRES_AT`
  - 재발급: 토큰을 바꾸면 이전 세션이 모두 무효가 된다(세션이 토큰 지문에 묶임).
  - 폐기: `/관리자 대시보드세션폐기`(감사 로그)
- **실패 기록:** 인증 실패는 IP와 경로만 기록하고 토큰 값은 기록하지 않는다. IP당 15분에 10회 실패하면 잠근다.
- **보안 헤더:** no-store, DENY, nosniff, CSP를 붙였다. 읽기 전용이며 GET만 허용한다.
- **세션 저장:** 세션은 메모리에 있다(단일 인스턴스 전제). 재시작하면 다시 로그인해야 한다.

### [1-6] 단일 인스턴스 전제와 중복 감지

- **리더 임대:** `services/instanceLock.js`가 SystemState `leader` 문서로 TTL 45초 임대를 15초마다 갱신한다.
- **부팅:** 임대를 얻기 전에는 디스코드 로그인, 부팅 복구, 주기 작업을 하지 않는다. 헬스 체크와 keep-alive는 계속 응답한다. 재배포 때 이전 인스턴스가 종료하며 임대를 반납하면 바로 인계받는다.
- **임대 상실:** 다른 인스턴스에 임대를 빼앗기면 알림 후 스스로 종료한다.
- **스케줄러 분리:** 주기 작업은 `services/scheduler.js`로 분리했다. 작업 정의와 실행 조건(`isLeader`)이 나뉘어 있어, 다중 인스턴스로 확장할 때는 `isLeader`를 분산 락이나 리더 선출 결과로 바꾸면 된다.
- **다중 인스턴스로 돌리면 문제가 되는 곳:**
  - 같은 봇 토큰으로 두 프로세스가 로그인하면 버튼 이벤트가 양쪽으로 들어간다. 테이블 상태가 메모리에 있어서 처리가 꼬인다.
  - 부팅 복구(`recoverPrevious`)는 "다른 인스턴스의 판"을 환불한다. 임대 없이 동시에 돌면 살아 있는 판을 환불할 수 있다.
  - 주기 작업(에스크로 스윕, 시즌 교체, 보스 종료, 클랜 주간 업적)을 두 번 실행할 수 있다. 각각 조건부 업데이트로 결과는 한 번만 반영되지만 알림이 중복될 수 있다.
  - 예측 창, 관전자 반응, 대시보드 세션, 비공개 방 코드 실패 횟수가 메모리에 있다.
- **결론:** 분산 락을 도입하기 전에는 다중 인스턴스 실행을 안전하다고 보지 않는다. 임대는 중복 실행 차단 장치다.

### 경제·악용 방지 규칙

- **보상 형태:** 신규 보상은 칭호, 배지, 테두리, 수집품, 보상 포인트, 기록 점수가 중심이다. 승률·배당을 바꾸는 능력치는 없다. 특별 규칙도 정산 결과를 **읽기만** 한다.
- **칩이 오가는 신규 경로는 셋뿐이다. 모두 지갑·에스크로를 거친다:**
  1. 클랜 생성 비용(`wallet.debit`, 원장 기록)
  2. 보스 처치 보상(`wallet.grantOnce`)
     - 처치 성공 시에만 지급하며, 1인 상한은 5,000칩이다.
     - 자격 조건: 계정 나이 14일 이상, 이 서버에서 실제로 5판 이상 플레이, 기여도 30 이상
     - `refId`로 중복 지급할 수 없다.
  3. 예측 칩(`wallet.reserve` → `settlement.batch`)
     - 관전자끼리 나누는 패리뮤추얼이고 하우스 몫은 0이다.
     - 적중자가 없으면 전액 환불한다.
     - 토너먼트 참가자 본인은 예측할 수 없다.
- **클랜:** 공동 지갑이나 클랜 간 칩 이동은 **넣지 않았다**. 경험치는 플레이 횟수와 승리 기반이며, 서버×유저당 하루 상한이 있고 클랜을 옮겨도 초기화되지 않는다. 탈퇴·추방·해산 후에는 24시간 재가입 대기가 있다. 시즌 보상은 3일 이상 소속된 멤버만 받는다.
- **랭크:**
  - 같은 상대와 하루에 반복한 판은 반영이 줄어든다(3판 이후 25%, 6판 이후 0).
  - 같은 상대에게 5판 이상 연승하면 `rank.suspicious` 감사 로그를 남긴다.
  - 비공개 방 판은 제외한다.
- **라이벌:** 상대 동의가 필요하고 최대 3명까지다. 상대에게 가는 알림은 신청 때 한 번뿐이다. 주간 도전 보상은 공개 게임만 세고 주 1회다.
- **비공개 방:**
  - 코드는 약 50비트이고 원문을 저장하지 않는다(sha256+salt). 비교는 상수 시간으로 한다.
  - 유저당 5회 틀리면 잠그고 `room.code-bruteforce` 감사 로그를 남긴다.
  - 방 판은 `detail.roomId`로 구분된다. 전적에는 🔒로 표시되고, 랭크·명예의 전당·라이벌 도전에서 제외된다.

### 시스템 연결 (명세 3절)

- **프로필:**
  - 이미지 카드에 클랜 태그와 시스템 배지(스토리 완주, 전당 기록, 랭크 리그)를 넣었다.
  - 임베드에는 특별 규칙, 스토리, 전당, 클랜, 보스 기여, 랭크, 예측, 수집 전시를 넣었다(`services/progression.js`).
- **업적:** 45종에서 69종으로 늘렸다. 규칙, 스토리, 전당, 클랜, 보스, 수집, 랭크, 예측, 라이벌 업적이다.
- **미션:** 새 활동형 미션을 추가했다.
  - 일일: 특별 규칙 완수, 보스 공격
  - 주간: 클랜원으로 40판, 스토리 2단계, 예측 2회
  - 활동형 미션은 게임 정산으로 진행되지 않고, 각 기능이 "한 번만 일어나는 지점"(조건부 업데이트 성공 직후)에서 올린다.
- **시즌:** 경제 시즌이 끝나면 다음이 함께 처리된다(`/관리자 시즌종료` 또는 30일 자동 교체).
  - 명예의 전당에 시즌 우승자 등록
  - 클랜 시즌 1위
  - 랭크 시즌 마감: 최고 등급 업적, 다음 시즌은 점수를 절반 초기화해서 시작
- **관리자 명령 추가:**
  - `정산상태`, `대시보드세션폐기`
  - `알림`(서버 알림 빈도: 모두 / 중요한 것만 / 끄기)
  - `기록익명화`
  - `보스시작`, `보스종료`, `클랜해산`
  - `보상이력`, `악용기록`

## 3. 데이터베이스 변경

모든 변경은 **추가**다. 기존 필드 의미는 바꾸지 않았고, 새 필드에는 모두 기본값이 있다.

**새 컬렉션** (괄호 안은 고유 인덱스):
- **안정화(1단계):**
  - `outboxevents` (eventId)
  - `transfers` (transferId)
  - `transferquotas` (economyKey+userId+day)
  - `settlementrecords` (settlementId)
- **진행·기록:**
  - `storyprogresses` (guildId+userId)
  - `halloffamerecords` (recordId)
  - `halloffamebests` (guildId+category)
- **클랜:**
  - `clans` (clanId · active 상태에서 guildId+nameKey)
  - `clanmembers` (guildId+userId)
  - `clanapplications` (pending 상태에서 clanId+userId)
  - `clanplayers` (guildId+userId)
  - `clanlogs`
- **보스·수집:**
  - `worldbosses` (bossId · active 상태에서 guildId+status)
  - `bosscontributions` (bossId+userId)
  - `usercollections` (userId+itemId)
- **랭크·방·예측·라이벌:**
  - `rankprofiles` (guildId+userId+gameType+seasonKey)
  - `privaterooms` (roomId)
  - `predictions` (tournamentId+userId+predictionType)
  - `rivalries` (guildId+pairKey)
  - `rivalmatches` (guildId+gameId+pairKey)
- **TTL:** `rivalmatches` 하나에만 7일 TTL을 걸었다(두 사람의 결과를 모으는 임시 데이터). 경제·기록 데이터에는 TTL이 없다.

**기존 컬렉션에 추가한 필드:**
- **users:** `outbox[]`, `txLog[]`, `escrow[].blocked`
- **profiles:**
  - 정산 처리: `processedEvents[]`
  - 특별 규칙: `dailyRule`, `ruleHistory[]`, `ruleCompletions`
  - 스토리·수집: `storyRewards[]`, `collectionSets[]`, `showcase[]`
  - 예측: `predict{}`, `predictProcessed[]`
  - 라이벌: `rivalWeekly`
- **ledgers:** `refId` (부분 고유 인덱스)
- **guildconfigs:** `notifyLevel`

**마이그레이션:**
```bash
npm run backup                    # 먼저 백업
npm run migrate:v3                # 드라이런: 모델별 인덱스·점검 결과
npm run migrate:v3 -- --apply     # createIndexes (기존 인덱스는 지우지 않음)
```
Mongoose `autoIndex`도 부팅 때 인덱스를 만든다. 다만 큰 컬렉션은 운영 전에 마이그레이션으로 미리 만드는 편이 안전하다.

**롤백:** 이전 버전을 다시 배포하면 새 필드·컬렉션은 무시되고 칩은 정상이다. 롤백 중에는 지갑에 쌓인 Outbox 이벤트가 처리되지 않지만, 다시 v3로 올리면 부팅 스윕이 이어서 처리한다.

## 8. 기존 동작이 바뀐 곳 (영향 범위)

1. **대시보드 `?token=` 주소가 동작하지 않는다.** 보안 요구 [1-5] 때문이다. 북마크를 `/dashboard/login`으로 바꿔야 한다.
2. **복구된 판도 전적·미션·업적에 반영된다.** 예전에는 제외했다. 명세 [1-2]에 따른 변경이다.
3. **송금:** 받는 사람 ID 형식(snowflake)을 검증하고, 한도는 `transferquotas`로 센다. 배포 당일 이전 송금분은 한도 집계에 들어가지 않는다(하루만 영향).
4. **정산 검증:** 게임 규칙 상한을 넘는 지급은 지갑에 반영되지 않고 보류된다. 상한은 게임별 최대 배당 기준이다.
5. **포커·토너먼트 정산이 `settlement.batch` 경로로 바뀌었다.** 결과 금액은 같고, 불변식 검사와 기록이 추가됐다.
6. **부팅:** 리더 임대를 얻을 때까지 디스코드 로그인을 미룬다. 재배포 때 이전 인스턴스가 종료하기 전까지 몇 초 대기할 수 있다.
7. **미션 풀:** 활동형 미션 5종이 추가되어 배포 당일 선택된 미션이 바뀔 수 있다. 진행도는 미션 ID별로 남는다.
8. **`npm test` 범위:** 이제 `test/*.test.js`만 돈다. 통합 테스트는 `npm run test:integration`으로 분리했다.

## 9. 알려진 제한 사항 · 구현하지 않은 부분

- **MongoDB 통합 테스트는 이 환경에서 돌리지 못했다**(위 7절). CI에서 확인이 필요하다.
- **대시보드·통계의 aggregation**(기존 기능)은 여전히 실제 DB에서만 검증할 수 있다.
- **보스 체력과 기여도:** 서로 다른 문서라, "기여도 반영 직후 체력 반영 전"에 프로세스가 죽으면 그 피해는 체력에 들어가지 않는다. 칩과 무관하고 보상은 기여도 기준이라 손해 보는 사람은 없다.
- **예측:** "우승자" 예측만 구현했다. "다음 탈락자·결승 진출자" 예측은 넣지 않았다.
- **랭크 리그:** 포커와 토너먼트만 대상이다(운 비중이 큰 게임은 제외). 봇 점수는 1000으로 고정이다.
- **비공개 방:** 초대 알림은 DM이 아니라 방 스레드 멘션으로 보낸다. 관전 비허용은 `Create Private Threads` 권한이 있어야 실제로 가려진다.
- **관전자 반응·예측 창·대시보드 세션은 메모리에 있다.** 재시작하면 사라진다(칩과 무관). 재시작 때는 진행 중 토너먼트와 예측 칩이 기존 복구 정책대로 환불된다.
- **연출:** "애니메이션"은 임베드 문구와 딜러 대사로 대신했다.
- **시즌 한정:** 샘플 1종(2026-27 겨울)만 있다. 새 시즌 아이템·챕터는 `content/collection.js`와 `content/story.js`에 기간과 함께 추가해야 한다(코드 배포 필요).
- **클랜 공동 지갑(보관금)은 넣지 않았다.** 칩 악용 경로를 만들지 않기 위해서다.
- **명예의 전당 익명화:** 관리자 명령으로만 한다. 탈퇴한 계정을 자동으로 감지하지는 않는다.

## 10. 운영: 장애 복구 · 백업·복원 확인

| 상황 | 처리 |
|---|---|
| 정산 직후 프로세스 종료 | 다음 부팅의 Outbox 스윕이 지갑에 남은 이벤트를 처리한다 |
| Outbox 처리 실패 반복 | `/관리자 정산상태`로 확인한 뒤 원인을 고치고 `재시도:True` |
| 정산 검증 실패(보류된 판) | `/관리자 정산상태` → `/관리자 복구 게임id:` (원금 환불, 감사 로그) |
| 다인 정산 일부 실패(partial) | 남은 판은 에스크로 스윕(20분, 포커 1시간, 토너먼트·예측 3~4시간)이 선기록 금액대로 정산한다 |
| 송금 중 종료 | 1분 넘게 멈춘 거래를 주기 작업이 이어서 처리하거나 취소한다 |
| 보스 보상 지급 중 종료 | 주기 작업(1분)이 `rewardState`가 `done`이 아닌 보스를 이어서 처리한다(중복 없음) |
| 중복 인스턴스 | 새 인스턴스는 대기하고, 임대를 잃은 인스턴스는 종료한다. 둘 다 알림을 보낸다 |
| 대시보드 토큰 유출 의심 | `DASHBOARD_TOKEN`을 바꾸고 재시작한다(이전 세션 모두 무효). 즉시 차단은 `/관리자 대시보드세션폐기` |

**백업·복원:** 기존 `npm run backup` / `npm run restore`는 DB의 **모든 컬렉션**을 대상으로 하므로 새 컬렉션도 자동으로 들어간다. `.github/workflows/backup.yml`의 일일 백업과 복원 리허설도 그대로 동작한다. 코드가 컬렉션 목록을 따로 들고 있지 않다는 점은 `scripts/backup.js`에서 확인했다.
